# E-PROC maintenance rules

These rules record defects found while implementing tenant isolation, operational logs, and tenant domains. Treat them as regression-prevention requirements, not optional guidance.

## Requirement precedence

- The latest explicit product decision wins over a previously inferred convention. Do not generalize a domain, role, or ownership rule when the user has named an exception.
- FSA-CLS currently uses the default domain `epoc.devfasttrack.com`. Do not change it to `epoc.fsa.devfasttrack.com` or another tenant-labelled form unless a later requirement explicitly requests that migration.
- Non-FSA tenants use `epoc.<tenant-slug>.devfasttrack.com`. The backend must derive this value from the trusted slug; the browser must never be the authority for tenant/domain ownership.

## Defects and mandatory prevention

| Defect found | Root cause | Rule that prevents recurrence | Required regression evidence |
| --- | --- | --- | --- |
| FSA-CLS was incorrectly converted to a tenant-labelled domain | A general subdomain convention was applied after an explicit request to retain the default FSA domain | Keep the FSA-only exception in `tenantDomainForSlug()` and document it in environment, deployment, Terraform, and maintenance files | Assert `fsa` and `fsa-cls` resolve to `epoc.devfasttrack.com`; assert `epoc.fsa.devfasttrack.com` is rejected for FSA-CLS |
| Existing FSA rows kept the old domain after source defaults changed | The startup update only replaced empty/localhost values | Migrations may replace only an explicit allowlist of known legacy FSA domains and URLs; never rewrite arbitrary customer domains | Run initialization twice, verify the second run makes no change, and verify assessment row counts before/after are identical |
| Domain changes could appear correct in UI while deployment still used stale values | Domain configuration is duplicated across application and infrastructure layers | Update the coupling set together: tenant context, control-plane validation/migration, provisioning validation, tenant UI, `.env.example`, nginx, Terraform variables/templates/examples, `AGENTS.md`, `rule.md`, and the E-PROC skill | Backend tests, frontend type-check, `terraform fmt -check`, `terraform validate`, and full build must pass |
| A valid-looking domain could belong to another tenant | Generic FQDN validation did not bind the label to the tenant slug | Backend approval and provisioning must compare the exact derived domain with the trusted tenant slug. Terraform validates allowed shape only; it does not replace backend ownership checks | Reject a correctly formatted domain whose label belongs to another tenant |
| Operational log controls could grant excess authority | UI role checks were treated as authorization | `admin` is read-only; matching `tenant_admin` may resolve, reopen, archive, and restore; superadmin observes selected-tenant logs only through the read-only control API. Enforce every rule in backend middleware and tenant-scoped SQL | Test regular-admin, cross-tenant tenant-admin, and superadmin mutation rejection |
| Archiving could destroy evidence | Full control was interpreted as physical deletion/edit access | Operational event content is immutable. Archive is a retained lifecycle state with actor/time metadata; there is no content-edit or physical-delete API | Verify archive preserves row/message and restore clears archive metadata without recreating the event |
| Remote log observation could expose credentials or cross tenant boundaries | Remote database access requires transient secrets and dynamic connections | Resolve slug/secret ARN from the control database, allow only PostgreSQL `LOG_DATABASE_URL`, scope every query by trusted slug, close the pool in `finally`, and return bounded safe errors | Test secret parsing, tenant parameterization, pool closure, and sanitized failure output |
| Changed documentation caused the harness to fail | Example documentation contained debug-like placeholders and realistic credential strings | Documentation examples must use visibly non-secret placeholders such as `<set-locally>` and must not contain unresolved debug markers or credential-shaped sample values | Run the same final harness against all changed code and documentation |
| Tenant and superadmin login shared one public endpoint | Frontend role redirection was mistaken for an authorization boundary, allowing both ownership planes to authenticate through `/api/admin/login` | Keep `/admin/login` + `/api/admin/login` tenant-role only and `/tenant/login` + `/api/tenants/login` superadmin only. Enforce scope after credential validation in the shared backend authentication service; frontend routing is UX only | Assert each role succeeds only at its own endpoint and valid credentials at the wrong endpoint return 403 without a token; assert protected redirects preserve the ownership plane |
| Production restart entered a persistent 502 loop when new database-plane variables/databases were absent | Deployment stopped PM2 before validating the production environment and relied on application startup to discover missing infrastructure | Keep real credentials outside Git. Require three explicit, distinct PostgreSQL URLs; run the validated, idempotent `npm run db:ensure` gate before replacing PM2; never print connection strings; fail deployment on an unhealthy origin | Test missing/duplicate/unsafe URLs, existing/missing databases, duplicate-create races, sanitized failures, and connection closure; validate deploy/setup shell syntax and health-check failure behavior |
| A private repository was treated as permission to commit deployment credentials | Repository access control was confused with secret storage and rotation controls | `.env.example`, specs, tests, and deploy logs contain variable names and visibly non-secret values only. Keep production values in `/opt/eaudit/.env` or a managed secret and rotate any value exposed outside that boundary | Scan the changeset with the harness secret rule and manually inspect staged diffs before commit |
| Deploy created databases but deferred schema migration until the new process started | Database existence and schema readiness were treated as one startup responsibility, so a failed plane migration could replace a healthy PM2 process or leave a fresh assessment database unusable | After `db:ensure`, run `db:migrate` for assessment, control, then log before PM2 replacement. Stop at the first failure, close all pools, keep errors credential-safe, and keep every migration idempotent/backward-compatible with the still-running process | Assert migration order, stop-on-failure, reverse cleanup, sanitized errors, two-run idempotence, preserved assessment row counts, and fresh `students` before `practice_submissions` schema order |
| Production failed with `Cannot find module 'base64-js'` even though the lockfile referenced it transitively | A critical Mammoth/Buffer runtime dependency was left implicit and deployment did not load-check the installed runtime closure before replacing PM2 | Keep `base64-js` as an explicit production dependency. After root `npm ci`, run `npm run deps:verify` before build/database/PM2 steps; fail with only the missing module name and never continue with an incomplete install | Assert the real critical modules resolve/load, every configured module is checked, loader details are sanitized, both deploy scripts invoke the preflight immediately after install, and a clean lockfile install contains `base64-js` |
| Preserving the main-branch Monaco editor could silently remove a newly merged anti-cheat signal | Rapid-insertion detection was implemented inside `CodeEditor.tsx`, coupling a forensic feature to a conflict-prone UI component | Keep cumulative rapid-insertion detection in the standalone detector service and call it from both exam/practice answer paths; keep single-event suspicious-paste detection in Monaco | Verify the detector ignores a single 300+ character change, flags cumulative 300+ characters within 2.5 seconds, observes a 10-second cooldown, and both exam modes report bounded metadata |
| Production frontend build failed while loading `@tailwindcss/oxide` | Tailwind v4 uses a platform-native optional package; deploy could omit it through npm configuration, and the EC2 bootstrap installed Node.js 18 even though Oxide 4.3.3 requires Node.js 20+, causing npm to silently skip the incompatible optional binding | Require the supported Node.js 22+ runtime in root/client manifests, install Node.js 22 in both EC2 bootstrap paths, reject older runtimes before `npm ci`, keep the Linux x64 GNU binding explicit in client `optionalDependencies`, install with `--include=optional`, and run the client native-dependency preflight before Vite | Verify both manifests/lockfiles require Node.js 22+, both Terraform bootstraps install Node.js 22, both deployment scripts run the runtime gate before install and include optional packages, the preflight loads Oxide, and a clean Linux `npm ci` client build passes |

## Source-of-truth boundaries

- `src/server/tenantContext.ts` owns runtime tenant-domain derivation and the FSA-CLS exception.
- `src/server/routes/tenants.ts` and `src/server/services/tenantProvisioner.ts` are the authoritative domain validation boundaries.
- `src/server/db/controlPlane.ts` owns the idempotent allowlisted legacy-domain migration.
- `client/src/pages/TenantManagement.tsx` mirrors the derived domain for UX only.
- `terraform/tenant-instance/**` owns provisioned DNS/application configuration. Legacy Terraform examples must not contradict the supported module.
- `src/server/middleware/auth.ts`, `src/server/routes/issues.ts`, and tenant-scoped issue SQL own log authorization; hidden buttons are never sufficient.
- `src/server/services/adminAuthentication.ts` owns credential/JWT policy; `adminAuth.ts` and `tenantAuth.ts` expose separate tenant and global login boundaries. Do not move role selection back into a shared frontend login.

## Required maintenance workflow

1. Inspect `git status` and preserve user-owned files, especially `data/Practice_M3_test.docx`.
2. Update the applicable design spec before a cross-layer behavior change.
3. Update every file in the relevant coupling set and add regression coverage for the original defect.
4. For schema/default migrations, use a temporary or local compatibility fixture, run initialization twice, and compare assessment row counts.
5. Run tenant tests, frontend type-check, full build, `git diff --check`, Terraform format/validation when infrastructure changes, and skill validation when maintenance knowledge changes.
6. Run `scripts/run-code-harness.py` with `--spec`; include every changed code/document file and exclude unrelated user-owned artifacts.
7. Do not commit, merge, push, provision, or change public DNS unless the user explicitly requests that action.

## Current acceptance anchors

- FSA-CLS default URL: `https://epoc.devfasttrack.com/`.
- Non-FSA example: slug `acme-vietnam` maps to `https://epoc.acme-vietnam.devfasttrack.com/`.
- Log ownership: `admin` reads, `tenant_admin` manages lifecycle for its own tenant, superadmin observes selected tenants read-only.
- Data ownership: assessment, global control, and per-tenant operational logs remain separate database planes.
- EC2 deploy ownership: `/opt/eaudit/.env` is the canonical secret file; bootstrap may create missing databases but never alters or deletes an existing database.
- EC2 schema ownership: `npm run db:migrate` initializes assessment, control, and log planes before PM2 replacement; normal startup repeats the same idempotent initialization as a safety check.
- EC2 dependency ownership: root `package-lock.json` and `npm ci` are authoritative; critical server dependencies must pass `npm run deps:verify` before any database or PM2 action.
- Legacy `terraform-ipv6` bootstrap ownership: `userdata.sh` must run `npm ci` → `deps:verify` → `build:server` → `db:ensure` → `db:migrate` before PM2, because RDS provisions only the assessment database while `.env` declares three planes and production startup fails when the control or log database is absent. Never call the removed `/api/init-tables`.
- `aws_instance.user_data_replace_on_change` must stay `true` in `terraform-ipv6`. cloud-init runs user-data only on first boot, so with the provider default (`false`) an edited `userdata.sh` is stored in state and never executed — the change looks silently ineffective.
- `terraform-ipv6` user-data ownership: gửi qua `user_data_base64 = base64gzip(...)` vì AWS giới hạn user-data ở 16384 byte và script bootstrap đã vượt ngưỡng; cloud-init tự giải nén.
- Mật khẩu database phải đi qua `urlencode()` khi ghép vào connection URL. Ký tự `#` làm URL không phân tích được (mọi thứ sau nó thành fragment) nên cả ba plane mất kết nối; `pg` tự giải mã percent-encoding nên giá trị nhận được vẫn đúng.
- Secret ownership của Terraform: giá trị thật (`jwt_secret`, `session_secret`, `db_password`) chỉ nằm trong `terraform.tfvars` — đã gitignore ở cả root và từng thư mục module. File `*.tfvars.example` được commit nhưng CHỈ chứa placeholder. `.gitignore` root chặn `*.tfvars`, `*.pem`, `*.key` cho mọi thư mục terraform; đừng liệt kê tên file cụ thể (đã từng ghi `eaudit-key-ipv6.pem` trong khi Terraform tạo `eaudit-key.pem`, khiến khóa riêng lọt vào git).
- Connection URL trong `terraform-ipv6` phải dùng `sslmode=no-verify`, không phải `require`. `pg` bản mới coi `require` là bí danh của `verify-full`, và tham số SSL từ chuỗi kết nối ghi đè tùy chọn `ssl` truyền trong code, nên `rejectUnauthorized: false` bị vô hiệu và Node ném `SELF_SIGNED_CERT_IN_CHAIN`. Bootstrap chết ở `db:ensure` với thông báo `Check connectivity and CREATEDB privilege` không kèm SQLSTATE, trong khi `psql` cùng URL vẫn chạy. Chuyển sang `verify-full` chỉ hợp lệ khi nạp bundle CA của RDS cho cả ba pool trong cùng một thay đổi.
- `no-verify` không phải giá trị libpq. Script shell dùng `psql`/`pg_dump` phải đổi sang `require` trước khi truyền URL, nếu không công cụ từ chối với `invalid sslmode value`.
- `backup-db.sh` phải neo `grep '^DATABASE_URL='`: không neo thì khớp luôn `CONTROL_DATABASE_URL`, `LOG_DATABASE_URL`, `DATABASE_MAINTENANCE_DB`. Truyền cả URL cho `pg_dump` thay vì dựng `PGPASSWORD`, vì mật khẩu trong URL đã urlencode.
- Script `deploy.sh` sinh bởi bootstrap không được xóa `package-lock.json`: `deploy/scripts/deploy.sh` chạy `npm ci`, lệnh này bắt buộc phải có lockfile.
- Thay `userdata.sh` là thay instance nên IPv6 đổi. Module không quản lý DNS (không có Route53; TLS kết thúc ở Cloudflare, nginx chỉ `listen 80`), nên bản ghi AAAA cũ trỏ vào máy đã terminate và site trả 522 dù máy mới khỏe. Cập nhật AAAA sau mỗi lần thay, hoặc vá tại chỗ qua SSM.
- `aws_db_instance` trong `terraform-ipv6` KHÔNG được đặt `ignore_changes = [password]`. `ec2.tf` nhét `var.db_password` vào `.env` qua user_data và không chịu ảnh hưởng của lifecycle block, nên bỏ qua thay đổi ở phía RDS tạo bất đối xứng: đổi mật khẩu trong `terraform.tfvars` thì EC2 nhận giá trị mới còn RDS giữ giá trị cũ, và `db:ensure` chết với SQLSTATE `28P01`. Kèm `apply_immediately = true`, nếu không thay đổi mật khẩu nằm chờ tới `maintenance_window` (sun 04:00) trong khi `apply` đã báo thành công.
- Phân biệt hai lỗi database của bootstrap qua SQLSTATE: không có mã kèm theo nghĩa là lỗi tầng TLS (`SELF_SIGNED_CERT_IN_CHAIN`, xem mục sslmode); `28P01` là sai mật khẩu; `28000` là RDS từ chối kết nối không mã hóa. Ba nguyên nhân khác hẳn nhau nhưng `db:ensure` in cùng một câu `Check connectivity and CREATEDB privilege`.
- `terraform-ipv6` phải ghi `SUPERADMIN_PASSWORD` và `FSA_TENANT_ADMIN_PASSWORD` vào `.env` từ `terraform.tfvars`. Không ghi thì seed dùng mặc định công khai trong lịch sử git. Hai biến không có default và validate >= 12 ký tự, để `plan` dừng ngay thay vì dựng xong mới phát hiện. Chúng chỉ áp dụng cho database mới — hàm seed không ghi đè tài khoản đã tồn tại.
